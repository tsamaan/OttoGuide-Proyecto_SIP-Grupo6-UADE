1. Objetivo

El Panel de Control de OttoGuide elimina la necesidad de interactuar con el robot mediante consolas SSH, proporcionando una interfaz gráfica intuitiva para el operador de la visita guiada. Sus objetivos principales son:

  • Orquestación: Facilitar el inicio y fin de la navegación autónoma y el pipeline de IA con un solo clic.
  • Monitoreo en vivo: Mostrar telemetría a 10 Hz para supervisar motores (temperatura, ángulo), batería (SOC, voltaje), e IMU.
  • Manejo de emergencias: Proveer un punto centralizado para detener todos los procesos del robot instantáneamente.
  • Simulabilidad: Poder desarrollarse y exhibirse sin requerir el hardware del robot mediante un modo "Mock".

2. Repositorio y estructura

El proyecto está organizado en un monorepo que separa la capa de captura y API (Backend, en el robot) y la capa de presentación (Frontend, en la notebook del operador).

Aplicación FastAPI principal del orquestador. Provee los endpoints de control unificados y el WebSocket de telemetría.

4. Flujo de datos (telemetría)

El flujo de lectura de métricas ocurre a alta frecuencia (10 Hz). La arquitectura evita sobrecargar la red agrupando todo en un único WebSocket.

  1. El robot (lowstate) publica su estado de articulaciones, batería e IMU en el bus local DDS (rt/lowstate).
  2. El Lector DDS del backend canónico lee este tópico asíncronamente y mantiene el frame de estado más reciente en memoria caché.
  3. El WebSocket de FastAPI (/telemetry) transmite a 10 Hz el caché del último frame hacia el frontend.
  4. En React, el hook useTelemetry recibe el JSON, alimenta el estado global y empuja los datos al histórico para su representación gráfica (Recharts).
Sin fallback silencioso: En el entorno de producción, está prohibido el fallback silencioso a telemetría simulada. Si falla la lectura DDS, el sistema fallará explícitamente para garantizar la seguridad operacional.

5. Flujo de control (botones)

El panel provee acciones principales de orquestación, cuyos efectos son manejados por el TourOrchestrator en el backend canónico.

Iniciar recorrido

Hace POST a /tour/start. El orquestador toma control del robot para la navegación autónoma. Actualiza estado a tour.

Iniciar charla

Hace GET a /content/script para iniciar la charla con el contenido conversacional de la IA.

Terminar ejecución

Hace POST a /emergency. El orquestador ejecuta una parada segura de todos los subsistemas. El estado vuelve a idle.

6. Contrato de API

MétodoRutaPropósito y Respuesta
POST /tour/start Inicia el recorrido autónomo. Devuelve el snapshot del estado actual.
POST /tour/pause Pausa el recorrido autónomo actual.
GET /content/script Obtiene el script conversacional activo.
POST /content/script/reload Recarga el contenido del script de IA.
POST /emergency Utiliza `terminal_safe` para detener los procesos de control de forma segura. Devuelve 200, 503 o 504.
GET /status Retorna {mode, running, llm_enabled, conversation_state}.
WS /ws/telemetry Conexión WebSocket que inyecta frames JSON cada 100 ms (~10 Hz).

7. Schema de telemetría

El frame (tanto real como mock) sigue esta estructura fija, la cual nutre todos los indicadores visuales: 

{
  "robot": "G1",
  "timestamp": 1718049182.2,
  "power_v": 27.5,
  "power_a": 3.5,
  "motors": [
    { "index": 0, "name": "L_Hip_Pitch", "group": "Pierna Izquierda", 
      "q_rad": 0.1, "q_deg": 5.7, "dq": 0.0, "ddq": 0.0, "tau_est": 1.2, "temperature": 35 }
    // ... 29 motores
  ],
  "imu": { "quaternion": [], "gyroscope": [], "accelerometer": [], "rpy_deg": [] },
  "foot_force": [45, 48, 50, 42],

Impacto en Frontend: Recharts grafica las métricas, y la UI expone alertas si la temperatura de un motor sobrepasa los 60 °C (con un límite de atención amarillo entre 40 °C y 60 °C).

8. Estados del sistema

Gestionado por el backend canónico, el estado actual de los procesos es interrogado por el front para renderizar la UI condicionalmente.

IDLE

  • Estado base o tras un Paro de Emergencia.
  • No hay navegación ni IA activa (running: False).

TOUR

  • Ejecutando recorrido (ottoguide-map corriendo).
  • running: True, llm_enabled: False (se habilitará al llegar a destino).

CHAT

  • Modo conversacional (otto_pipeline corriendo).
  • running: True, llm_enabled: True.
  • Tiene un subestado asociado: conversation_state (hibernación, escuchando, procesando).

10. Modo mock vs. real

Tanto el Front como el Back implementan "Mock Mode" para facilitar el desarrollo:

  • Back: En producción, SILENT_REAL_FALLBACK = PROHIBITED. No hay fallback silencioso a stub; si falla la conexión real con el hardware, el sistema debe reportarlo explícitamente en lugar de enmascararlo con datos simulados.
  • Front (VITE_MOCK_MODE=true): Por defecto activado, ignora el websocket del backend y procesa las respuestas simuladas del mismo navegador, ideal para diseño de interfaz pura (aislamiento total de redes). Esto puede desactivarse desde la UI usando el toggle de "Modo simulación".

12. Despliegue y primer arranque

El flujo de despliegue en hardware real se realiza siguiendo PRIMER_ARRANQUE.md.

  • Compilación Backend: Construir el Docker en la máquina ARM64 (robot) es mandatorio, porque se compila CycloneDDS de forma nativa. docker compose up -d --build debe ejecutarse en la Companion PC.
  • Arranque Seguro: El contenedor Docker utiliza restart: always para reiniciarse si se cae, y levantar automáticamente con el Daemon del SO del robot.
  • Red LAN: Configurar el IP de la notebook del usuario en 192.168.123.X/24 mediante RJ45 y setear la URL del host FastAPI en el Frontend.
