1. Objetivo

OttoGuide propone un robot co-guía para visitas universitarias de UADE, orientado a mejorar una experiencia concreta: recorridos de admisión más memorables, homogéneos y diferenciados, aprovechando un activo tecnológico existente sin reemplazar el rol humano del guía.

Este documento cubre el pilar de movimiento, HIL, sensores y preparación de autonomía. Su objetivo es dejar una base técnica validada para:

  • Conectar de forma segura con el robot real Unitree G1 EDU / Ottoman.
  • Validar el entorno físico, red HIL y runtime ROS.
  • Leer sensores y registrar datos del entorno.
  • Generar artifacts reproducibles para replay y análisis offline.
  • Preparar el camino hacia mapeo, waypoints y navegación autónoma futura.
  • Operar scripts de captura sin comandos de movimiento ni publicación de /cmd_vel.
Este documento no desarrolla en profundidad el pilar de interacción con IA. Ese pilar se vincula con conversación, experiencia verbal y APIs de IA; aquí el foco es movimiento, sensores, HIL, artifacts y seguridad.

4. Entidades técnicas principales

Estas entidades ordenan el flujo técnico del pilar de movimiento y permiten hablar de captura, mapeo y navegación sin mezclar estados validados con pendientes.

RUN_ID SESSION BAG_DIR Rosbag Topic ROS Frame Map PGM/YAML Waypoint Sensor stack Artifact package Safety gate Endpoint/API Estado validado

Identificadores de captura

RUN_ID, SESSION y BAG_DIR trazan cada corrida, su carpeta de trabajo y el rosbag resultante.

Datos robóticos

Un rosbag contiene topics ROS, frames y mensajes de sensores para replay/offline.

Mapa y waypoints

PGM/YAML y waypoints son resultados posteriores al mapeo; no están validados como producto final en el runtime actual.

Safety gate

Conjunto de reglas que impiden mover el robot desde scripts de captura y evitan publicar /cmd_vel.

5. Flujos principales

Preflight de campo

./tools/hil/ottoguide-map prep

Valida ROS/CycloneDDS, sensor stack y topics raw. Fue ejecutado en validación documental: PASS para captura raw y PARTIAL por falta de TF/map.

Captura raw

./tools/hil/ottoguide-map start --label "office_short_remote_control_raw"

Inicia grabación de sensores disponibles. No fue ejecutado durante esta validación documental.

Monitoreo

./tools/hil/ottoguide-map status

Consulta PID, estado del rosbag, tamano y logs de la sesion.

Stop limpio

./tools/hil/ottoguide-map stop

Cierra el rosbag con SIGINT al PID, evitando cortes bruscos.

Finalizacion

./tools/hil/ottoguide-map finalize

Genera ros2 bag info, manifiestos, hashes y solo intenta mapa si existe /map.

Empaquetado

./tools/hil/ottoguide-map package

Crea un paquete transferible a notebook para análisis offline.

Análisis offline

Incluye replay del rosbag, reconstrucción o provisión de TF, SLAM, limpieza de mapa, waypoints y validación offline antes de cualquier prueba física de navegación.

6. Captura, mapeo y navegación

Captura raw

Disponible parcialmente

Validada con /utlidar/cloud, /livox/imu y /scan. Sirve para rosbag y replay/offline aunque no haya TF.

Mapeo completo

Pendiente de validación

Requiere /tf, /tf_static, /odom y /map. No se presenta como mapa apto para navegación.

Navegacion autonoma

No validada

Requiere mapa, localización, safety gates, Nav2 físico por validar y control seguro de /cmd_vel.

Interpretacion actual

El MVP actual debe centrarse en captura sensorial y trazabilidad. La autonomía física queda fuera hasta nueva evidencia.

Límite técnico: la ausencia de TF, odometría y mapa impide presentar navegación autónoma o mapeo completo como validado.

11. MVP técnico propuesto

El MVP del pilar movimiento no es demostrar autonomía total de inmediato. Es construir una base confiable y trazable para llegar a ella.

Disponible

  • Conexión HIL estable.
  • Robot sincronizado a baseline.
  • Sensores raw activos.
  • ottoguide-map prep validado.

Preparado

  • Captura raw reproducible.
  • Empaquetado de artifacts.
  • Replay offline.
  • Manifiestos y hashes.

Pendiente técnico

  • Reconstrucción/provisión de TF.
  • SLAM/mapa.
  • Waypoints.
  • Validación de localización.

Futuro controlado

  • Navegación física controlada.
  • Safety gates.
  • Validación de /cmd_vel.
  • Pruebas incrementales.
Alcance recomendado: defender como MVP técnico la captura raw validada, la trazabilidad de artifacts y el camino verificable hacia mapa/waypoints/navegación, no una autonomía física aún no probada.

12. Decisiones MVP cerradas

  • No mover el robot desde scripts de captura.
  • No publicar /cmd_vel.
  • Usar control remoto humano en primeras capturas.
  • Mantener artifacts pesados fuera de Git.
  • Usar ottoguide-map como ejecutable de campo.
  • Usar b07d362 como baseline actual.
  • Aceptar raw capture sin TF para replay/offline.
  • Exigir TF/odom/map para mapping completo.
  • Dejar navegación autónoma fuera hasta nueva validación.
  • Documentar puertos cerrados como no expuestos observados, no como bloqueos del fabricante.

13. Fuera del alcance actual

  • IA conversacional en detalle.
  • Navegación autónoma física.
  • Repetición automática del recorrido.
  • Publicación de /cmd_vel.
  • Modificación o activación de locomoción.
  • APIs oficiales Unitree no validadas.
  • Operacion cloud como dependencia del recorrido.
  • Reemplazo total del guía humano.

14. Pendientes y no verificados

Pendiente técnico

/tf, /tf_static, /odom, /map, /map_metadata, Nav2 físico, SLAM runtime y safety gate de locomoción.

Pendiente documental

Datos oficiales de fábrica, APIs oficiales Unitree, puertos oficiales del fabricante y significado de servicios 4000, 1026, 23366, 23367.

Pendiente operativo

Captura raw real, copia de artifacts, replay offline, provisión de TF, mapa, waypoints y validación segura de navegación.

No verificado

Todo dato de fabricante o autonomía física que no tenga evidencia runtime u oficial debe quedar marcado como no verificado.
